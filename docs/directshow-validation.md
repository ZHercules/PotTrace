# DirectShow 图内采集验证（2026-11-17）

**结论：来源采集原型可行，完整准确性验收尚未通过，不部署。** 在本机两个隔离副本中，已覆盖首次启动、同名不同目录的影片切换和自然下一集，取得实际连接来源的完整路径。载入边界与当前图归属仍有缺口，不能宣称已经消除所有漏记，也没有把取证事件写入正式历史数据库。

原型位于 `probes/DirectShowProbe/`。复现见其 [README](../probes/DirectShowProbe/README.md)；结构化摘要见 [directshow-evidence.json](diagnostics/directshow-evidence.json)。全部原始日志、测试配置和播放器客户区截图保留在摘要标明的 `out/graph-probe-*` 中。

## 已验证的行为

| 场景 | 观察结果 | 结论范围 |
|---|---|---|
| 原安装版本 26.4.22 的隔离副本，AVI / MP4 / MKV | 首开、切换、自然下一集均取得正确完整路径；同名不同目录可区分 | 来源取证通过，不等于正式统计已通过 |
| 官方 26.10.21 隔离副本，MP4 / MKV | 同样能取得完整路径；内置 Direct3D11 渲染器可正常播放 | 来源通过，图与窗口归属未通过 |

| 预加载后取消，直接关闭播放器 | 下一集已打开，但没有下一集的已连接运行记录 | 取消场景未产生虚假的下一集来源事件 |
| MKV 停止、重开、无效 MP4、恢复有效文件 | Stop/销毁可见；重开来源正确；无效文件无已连接运行记录；随后恢复正常 | 两个版本均通过这组基本恢复检查 |
| 不挂载滤镜的对照 | 同样完成启动、暂停、跳转、切换、下一集、停止、错误恢复 | 未观察到挂载后的崩溃/退出故障；样本不足以证明长期无性能影响 |

上述通过用例均正常退出，没有被测试工具强杀；图内日志丢失计数为 0，已运行实例均有 Destroy 尾部记录。原型尚未做长时间压力测试、硬解码配置矩阵或高分辨率性能验收。

### 捕获到实际的回调延迟

在 `graph-probe-1794857531693125900`（新版 MP4、预加载）中，时间均相对启动命令，使用同一原生时钟：

| 事件 | 时间 |
|---|---:|
| A 的已连接 PauseAfter，直接来源为 A | 1,531 ms |
| A 的已连接 RunAfter | 1,641 ms |
| A 的 StopAfter | 7,860 ms |
| B 的已连接 RunAfter，直接来源为 B | 8,438 ms |
| 脚本补发 A 的 Start，以及 A 的 Pause/Resume/Close 和 B 的 Open/Start | 8,953 ms |

这次 A 的图内 Run 比脚本 Start 早 **7,312 ms**，B 的来源也早于 B 的脚本 Open。该数据证明本次图内取证不必等待延迟脚本回调；它不是所有机器的最大延迟上界，也不是影片载入时刻的精度承诺。

### 暂停时间与预加载

恢复型预加载用例的原生 PauseAfter→RunAfter 区间分别为 11,578 / 11,594 / 11,672 ms，包含独立截图和文件句柄检查的时间。暂停后位置查询存在一次缓存更新；稳定后的采样位置分别保持 985 / 1,096 / 1,033 ms，没有继续前进。

暂停区间和其来源可被图内事件保留，有望用于用户要求的“暂停只计有效停留，不计实际播放时长”。**当前尚未接入统计引擎验证 10 秒判定和数据库累计值，不能称这部分已经完成计入。** 下一集文件句柄的存在只证明提前打开；不推断其已完成解码或预滚。

## 两个关键限制

**1. 图枚举不满足完整性判断，改为直接连接取证。**

实测 `IEnumFilters::Next` 枚举出若干滤镜后返回 `0x80004005 / E_FAIL`。官方接口文档规定数量不足应返回 `S_FALSE`；不能把失败当成正常结束。因此原型保留 `uncertain=true`，不再用“枚举只看到一个路径”证明来源唯一。[微软接口说明](https://learn.microsoft.com/en-us/windows/win32/api/strmif/nf-strmif-ienumfilters-next)

替代取证沿本滤镜**实际输入端的连接**取得上游滤镜，再调用该对象的 `IFileSourceFilter::GetCurFile`。实测 AVI/MP4/MKV/Seamless Source 都成功返回完整路径。这样可以说明这条输入流的来源；如果未来连接到不提供该接口的解码器或其他组件，就必须报告未知，不能退回按标题、文件时长或进程命令行猜测。[GetCurFile 接口说明](https://learn.microsoft.com/en-us/windows/win32/api/strmif/nf-strmif-ifilesourcefilter-getcurfile)

**2. 还不能把来源与滤镜状态直接认作当前影片的精确载入事件。**

- Join 包含未连接、随后放弃的构图尝试，不能算载入。Pause 用于预滚，首样本也可能在真正运行前出现。官方状态定义并未赋予这些事件“PotPlayer 当前影片载入完成”的含义。[DirectShow 状态说明](https://learn.microsoft.com/en-us/windows/win32/directshow/filter-states)
- 自动下一集的预加载模式会复用同一图和同一采集实例；一次切换可能出现重复 Pause/Run。同一实例不能直接作为一条播放记录的 ID。
- 原副本的 EVR 能通过标准接口提供属于当前主窗口的渲染 HWND。但根窗口相同仍不足以普遍排除同进程的预览图，相关竞争场景尚未验证。
- 新版 `Built-in Direct3D11 Video Renderer` 对 `IVideoWindow` 和 `IMFGetService` 均返回 `E_NOINTERFACE`（`0x80004002`）。目前没有可用于产品自动识别的图与显示窗口归属证据。红/蓝截图只是本次测试的外部旁证。
- 外部状态查询与滤镜变化并非原子：部分用例先查询到 Playing，稍后才收到滤镜 Run。也不能将外部状态查询开始时间回填为精确载入时间。
- 时间戳使用 `GetTickCount64`，有时钟粒度；身份查询另有开始/结束区间。测得查询耗时 0 个 tick 不代表零开销，更不代表任意第三方滤镜不会阻塞。

因此，仍须证明当前媒体归属、载入边界以及首次即暂停的边界关系，才能用它替换正式统计入口。仅验证“比脚本快”不足以允许部署。

## 对照与失败记录

两个版本不挂载滤镜的 MP4 对照首次可观测活动时间均为 1,594 ms。所列挂载用例约为 1,515–1,766 ms；样本少、运行环境存在抖动，不能据此认定无性能损耗。一次新版挂载用例有 300 ms 外部查询超时，随后正常继续；此前不挂载滤镜也出现过同类查询超时。查询超时记为未知，没有假造状态或认定崩溃。

调查过程中的失败保留如下，未纳入通过用例：

- `1794856040382930900`：测试误用精确 30,000 ms 匹配 MP4；AAC 封装时长为 29,994 ms。只修正合成文件识别的容差，没有修改 5 秒/10 秒统计阈值。
- `1794856867415500500`、`1794856940761224400`、`1794856992053714600`：枚举完整性断言失败。最后一个已记录直接上游来源成功；随后将两种证据分开，保留枚举失败。
- `1794857237359357300`：测试只接受停止状态 0，但此配置停止会卸载媒体并返回 -1；图已记录 Stop/Destroy。修正为接受停止或卸载，并要求独立图内 Stop 证据，复测通过。
- `1794857424907729500`：校正 DPI 后，窗口中心落在播放列表边缘，中心像素断言失败。截图实际仍是红色当前集。改用客户区内大面积纯色旁证，排除少量 UI 文字，完整复测通过。未将此失败解释为播放器错播。

## 下一阶段及部署门槛

1. 建立可靠的当前图归属和载入锚点，覆盖首次即暂停、预览图及取消构图；对不支持的渲染器明确保留未知，不能静默误计。
2. 在隔离环境将已确认身份及原生时间线接入统计引擎；处理图复用、重复边界和延迟脚本事件，验证停留严格大于 10 秒、片段严格大于 5 秒、暂停不累计播放时长。
3. 完成硬解码/不同渲染器、长时间切换、故障退出与恢复、睡眠排除和数据库实际计入的验收；重新发布可回退安装包。

原型仅私有载入隔离副本，未做系统 COM 注册；正式 `E:\pot\PotPlayer` 未部署本原型。测试 WebView2 使用独立工作区目录，不改变用户数据目录 ACL。原有产品及预览包仍保留先前的准确性限制。
