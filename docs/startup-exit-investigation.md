# 早期启动退出调查（2026-11-18）

**结论：原始那次退出的根因仍未确认，不能声称播放器启动退出已修复。** 本轮修复了实播工具的启动证据缺口与一个可重复的窗口检查竞态。生产采集器代码未因猜测而修改，稳定版部署仍被阻止。

## 原始证据及限制

失败目录 `out/collector-probe-1794989204361325000`：2026-11-18 16:06:45 左右启动，16:07:01 写结果；报告仅有 `Player exited before window`，没有 PID、退出码、加载模块或进程转储，数据库无会话。原报告保留原样。

失败及紧接着成功轮次 `1794989305193799700` 的 AX 均为 SHA-256 `20c743733ddc4998bb7aa387ee1311d4936a2bf75e5260172b255c575e84ddca`；保存的播放器 INI 只有 AX 所在证据目录不同。原始 Bridge 哈希已知，但未找到对应旧二进制，因此本轮旧 AX 对照使用当前 Bridge，不能称为完全相同二进制的历史回放。

检查了对应时间段的 Windows Application 日志、PotPlayer 的 WER 归档、用户崩溃转储目录及隔离目录，没有找到能解释该退出的崩溃记录。失败目录的 WebView2 配置存在正常退出标记；这只说明浏览器配置有该标记，不能推断播放器一定正常或一定由人工关闭。用户无法确认当时是否关闭过窗口，人工关闭保留为未确认可能性。

顺序对照的观测中，主窗口先出现，Bridge 和 AX 随后才被看到加载。例如首轮早期 AX：窗口约 531ms，Bridge 1172ms、AX 1203ms。这支持继续检查播放器自身启动阶段，但采样只能证明这些轮次的观测顺序，不能证明原始失败中 AX 未加载。启动状态查询偶尔超过单次 400ms，之后在有界等待内成功；这些超时不会被当作开始播放。

这些结果不支持“这个 AX 必然导致退出”“全新路径必然失败”或“两个实例交叠必然导致新实例退出”，也不排除偶发故障。原进程已结束且关键证据未保存，无法事后恢复其退出码或调用栈。

## 已确认并修复的问题

`run_collector_probe.py` 以前只在最终结果中保存笼统异常，最早版本连退出码也未写入。新 `player_startup.py` 在清理前独立保存每次启动的 PID、单调时间、窗口/模块/子进程快照、结果以及有符号退出码与 32 位十六进制表示，正常退出码 0 也不遗漏。每个启动尝试有独立文件编号，避免 PID 重用覆盖证据；快照有数量上限，重复状态不反复写盘。

原来的窗口检查先接受窗口，再检查进程是否退出。当进程在枚举窗口期间退出时，测试可错误地返回已失效窗口。确定性反例证明旧顺序失败，新实现枚举前后核对所属进程，不接管其他 PID 的窗口。退出、窗口超时、诊断读取异常各自记录；刚好在截止时退出也归为退出而非仍存活的超时。

不做自动重试或自动接管另一进程，以免把偶发退出掩盖为通过。**这个窗口竞态与证据修复不能解释原始那条 `exited before window`，两者不能混称根因修复。**

回归覆盖：提前退出码 0、异常码 `0xc0000005`、截止时退出、枚举期间退出、其他 PID 窗口拒绝、正常窗口、诊断读取失败后恢复，以及真实子进程退出码 0/23。新 8 项与既有 6 项 Python 验证器测试合计 14 项通过。旧窗口优先顺序在对应竞态反例中先失败，再验证新实现通过。

## 后续判定

再次出现退出时，优先读取该轮 `startup-<尝试编号>-<PID>.json`，区分程序退出、窗口未就绪以及采集模块是否已被观察到加载，再决定是否需要异常转储、调用栈或针对该组件的修复。退出码不能单独证明谁发起了关闭。原始失败仍是稳定性验收未闭合事项，不能将重复成功或新日志功能计为根因已消除。
